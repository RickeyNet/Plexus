# Changelog

## Unreleased

- Topology: in the **Tidy tree** layout a device's links to the sites hanging off it (a VPN hub's spokes, a VPC's peers, the Cato backbone's PoPs) are now drawn as a comb: down from the device to a bar above the row of sites and a straight drop into each, coming down beside a site's internet gateway or WAN uplinks rather than through them. When the sites wrap onto several rows, a trunk down the left of the block carries the bar to each lower row, so no link runs through another site's box; they used to be curves fanning out from the device, crossing the sites between and running through the boxes of the first row on their way to the next. The device now sits in the middle of its spokes, over its own devices, instead of at the far left of the row with every link fanning out one way. The Cato PoPs stay in one row, on one comb. A site title that would run into the next site's box (a long name over a narrow box, such as a VPC that was not collected) is shortened with an ellipsis; the full name is still in the tooltip and the details panel. A dragged device keeps its comb link, with a straight stretch to where it was dropped. The HTML export follows, as it uses the same layout.

- Topology: the HTML export's details panel no longer breaks an address or an ID over two lines. Its table cells could be broken anywhere to fit the panel, so an instance's `10.210.2.20` in a VPC's **Instances** table was drawn as `10.210.2` over `.20`, and `i-0f3c001` broke at its hyphen. A cell that is one word now stays on one line, in the export and on the Topology page's details panel, and a table too wide for the panel scrolls sideways under a scrollbar that is always drawn; only a key/value's value may still break a long ID or ARN.

- Topology: in the **Tidy tree** layout a device with no links (a dormant or offline access point, switch or appliance, or a sensor the API reports no neighbour for) is now drawn with its site: in a small grid under the site's gateway, inside the site's box, after the gateway's other devices. It used to go in the grid under all the trees, which drew most of those sites twice, each part in a box of its own (on a 3,700-device organization, 113 of the 120 devices there belonged to a site already in a tree). Only devices whose whole site has no links, and inventory devices in no group, stay in the grid under the trees. The unlinked customer gateways of the **AWS transit and VPN** box now sit under its transit gateway, in one box. The HTML export follows, as it uses the same layout.

- Topology: the AWS map now shows which EC2 instance an inventory host is. A host can name its instance outright with the new **AWS instance ID** (`aws_instance_id` on `POST /api/inventory/{group}/hosts` and `PUT /api/hosts/{id}`, returned on every host row; stored trimmed, matched in any letter case, `i-` and hex or HTTP 422), which is checked before the IP match, so a host whose inventory address is not one AWS records (a NAT or load-balancer address) still becomes its instance's node, and a host that names one instance is no longer matched to another by address. An instance that becomes an inventory host after the last discovery - a host added later, or given its instance ID - is now drawn, linked to its VPC, as soon as the map is next loaded instead of waiting for the next discovery: the AWS snapshot keeps every instance that is not a node aside (`latent`), and `/api/topology` puts the ones that match a host on the map, with their details on `GET /api/meraki/nodes`. Every instance node carries its instance ID and subnet: the instance Overview gains a **Subnet** row, `/api/topology` nodes of an AWS instance carry `meraki.instance_id` and `meraki.subnet`, and every node that is an instance - also a host already drawn as a Meraki or Cato device, with AWS in `also_providers` - carries `instance` (`provider`, `id`, `subnet`, `vpc`, `org_ref`, `node_id`) so the Overview tab and tooltip can show it; the HTML export's nodes carry `instance_id` and `subnet`. New column `hosts.aws_instance_id` (migration 0069).

- Topology: the default **Tidy tree** layout now runs top to bottom and keeps each source together. The inventory, Meraki, Cato, AnyConnect, AWS and Azure are each a region of their own, side by side from left to right with their tops level, framed and titled with the source's name when the map has more than one; links between sources are still drawn but no longer pull a device into another source's tree, so Cato sites are no longer scattered among Meraki ones. Trees grow down from their gateway, with an appliance's WAN uplinks in a row above it; a Cato account hangs off its backbone, then its PoPs, then the sites and users of each PoP. Eight or more leaf devices of one site under one device (access points, remote users) form a grid under it, and a row of children too wide for the screen (a VPN hub with hundreds of sites) wraps onto several rows under its parent, in site name order, instead of each site being cut out as a block of its own. Nodes pinned by dragging keep their saved positions; **Reset Positions** re-lays them.

- Topology: the links from the Cato Cloud to its PoPs are always drawn. On a map with more than 300 VPN tunnels they were hidden with the rest until a device was selected; they no longer count towards that limit, and **VPN Tunnels** on the Topology page and **All tunnels at once** in the HTML export apply to the other tunnels, Cato's site and user links included. The HTML export marks them with `backbone: true`.

- Topology: the details panel can now be dragged wider by its left edge (double-click the edge to go back to the default width), and it remembers the width for every tab. Tables wider than the panel, such as a VPC's **Instances**, show their horizontal scrollbar instead of silently cutting a column off at the panel's edge.

- Cato: each PoP is now a **PoP <name>** box holding the PoP and the remote users connected to it, instead of the PoPs sharing the **Cato Cloud** box and their users being in a separate **Remote users - <PoP>** box; the **Cato Cloud** box holds the backbone node, and users with no PoP keep a **Remote users** box. The PoP is drawn over its users in the snapshot and the HTML export too, and leaves under one device there form a grid wider than 5 columns when there are more than 25. In the Topology tidy tree the PoPs stay in one row under the Cato Cloud instead of wrapping onto several, so the always-drawn backbone links reach every PoP without crossing another PoP or a user. Collect the Cato account again to get the new boxes.

- Cato: fix the site query, which Cato refused (`Cannot query field "keys" on type "HaStatus"`), so every collection fell back to the basic site list without WAN links, Sockets, interfaces or HA state. HA status now reads `keepalive` and `socketVersion` (there are no `keys` or `routes` fields) and interface bandwidth reads `upstreamBandwidth` / `downstreamBandwidth`, matching Cato's published schema. A refused query now reports every message Cato returned, not just the first, so one collection names every field Cato rejected. With the full query accepted, the build no longer crashes on a site's IPsec settings, which Cato returns as a list of tunnels: the **IPsec tunnel** section is now a table with one row per tunnel (primary first), and the other object fields Cato returns (HA status, Socket info, WAN link location and settings) are read whether they come as one object or a list.

- Topology: a Cato vSocket or Meraki vMX that runs on an AWS instance is shown with the source selector on **AWS only** too (it was left out, as a Cato or Meraki device), and a vSocket keeps its tunnel to its Cato PoP there, so the AWS view shows where its VPN goes. The same goes for a device that is the far end of a VPN of another integration (an AWS customer gateway). `/api/topology` marks such a node with `also_providers`, and the HTML export's source selector honours it the same way. When Cato refuses the full site query, the collection now tries a reduced query that still reads each Socket's WAN links before falling back to the basic site list: those links' public addresses are what match a vSocket to its instance.

- Topology: in the tidy layout a link between two sources (a Cato vSocket or Meraki vMX and its AWS VPC, an inventory device and a Meraki one) no longer runs straight through the sites in between. It rises from each end, around the boxes of the other sites and the devices in its way (the cheapest path with few turns on a grid made of their edges), to a lane above the source frames, and crosses there: links whose stretches overlap get lanes of their own, the shorter one lower, and links are kept from running on top of each other. Such links keep their colour, dashes, label, dimming, path highlighting and tunnel hiding, and clicking one opens its details. On the test data the ten links between sources went from crossing 4 to 40 devices each to crossing no device and no other site's box, routed in about 20 ms.

- Topology: the HTML map export is laid out like the page's **Tidy tree**, by the same code, instead of packing every site of every source into one grid: a region per source, each network a tree in boxes that do not overlap (the site's name above its box), and the links between sources routed around the other sites and over the regions. `npm run build` also bundles the layout as `dist/viewer-layout.js`, which the export inlines; each exported device carries the few fields the layout reads (`topo`) and each link its `protocol`. Picking one source in the file lays that source out again. Without a built frontend the export keeps the old grid.

- Map Sources: collection warnings are listed in the dialog itself. The warning badges of a source, of the collection history and of the "Map updated" note open a list of the API calls that failed or were refused (scope, request, HTTP status, message), read from the new `GET /api/meraki/snapshots/{id}/warnings`; `/api/topology/sources` now returns each Meraki, Cato and AnyConnect source's `snapshot_id`. Previously the warnings were only in the HTML map's Report.

- Cato: every connected remote user is now a node of its own (person icon, `kind: "user"`) instead of one **Remote users** node. Users are grouped in a **Remote users - <PoP>** box per PoP and linked to their PoP, so a PoP that no site uses shows why it is on the map; the Topology tree lays them out as a grid under the PoP and keeps them with it on a large map. A user's details say where they connect from (remote or which office, public IP, ISP, city, state, country, coordinates), what they are connected to (PoP, VPN IP, uptime), their device (name, OS, Cato Client version) and their recent connections; each PoP and box lists its users with VPN and public IP. The users query now also reads recent connections, phone number and the full IP location, and falls back to the previous query if Cato refuses it. The HTML export lays out a large set of unlinked nodes wider than 8 columns.

- Add Azure to the Topology map, the same way as AWS. Every enabled Azure subscription that Cloud Visibility has discovered is built into one snapshot in the Meraki snapshot format (`org_ref` -2) and merged into `/api/topology`, so it is covered by node details, deep search, Path Mode and the HTML export. Each VNet is a framed site whose router node owns the VNet's subnets, with its VPN and ExpressRoute gateways, NAT gateways and Azure Firewall; ExpressRoute circuits and local network gateways form an **Azure VPN and ExpressRoute** box; peerings and gateways are cloud links, and a site-to-site or VNet-to-VNet connection is a tunnel that is down when Azure reports it not connected. Virtual machines are read from their network interfaces and are nodes only when they forward traffic (IP forwarding on) or are inventory hosts; the rest are listed and searchable in their VNet. Local network gateways, Azure VPN gateways and virtual appliances are joined to Meraki, Cato and inventory devices by public address, like their AWS counterparts. The Azure collector now also reads subnets (with their route table, network security group and NAT gateway), every route of each route table, the subnets and interfaces each network security group is applied to, peering options, gateway public IPs and BGP settings, local network address spaces, ExpressRoute peerings and gateway connection status; public IP addresses, NAT gateways, network interfaces and Azure Firewalls are best-effort sections recorded as `collection_warning` resources when denied. Gateway shared keys are never read. Its reshaping lives in `netcontrol/integrations/azure`. Path Mode checks an end in a VNet against Azure's effective routes (VNet, peerings, the hub gateway a spoke uses, user-defined routes, routes that drop traffic) and the network security groups of subnets and interfaces, default rules and the `VirtualNetwork` / `Internet` tags included; an Azure Firewall, a BGP- or ExpressRoute-learned route or an unknown service tag gives *check incomplete*. New `GET /api/meraki/azure/reachability`. A path between AWS and Azure gets both checks. `POST /api/meraki/sample?provider=azure` (**Load Sample → Azure**) adds a demo subscription, which is also the Azure sample discovery of Cloud Visibility. The Sources dialog lists Azure subscriptions next to AWS accounts. Guide: `docs/azure-topology.md`.

### Compliance
- Add **Meraki** security compliance. A compliance profile may now carry rules of type `meraki` that name a check against the Dashboard API configuration of a Meraki organization - the Meraki equivalents of the IOS switch/firewall/wireless hardening controls: DHCP server policy *block* (DHCP snooping) and ARP inspection, rogue DHCP alerting, RSTP and a pinned root bridge, storm control; per switch port an access policy (sticky MAC / MAC allow list / 802.1X access policy, the port security equivalent), sticky MAC limit, BPDU guard on access ports, root/loop guard on trunks, native VLAN not 1, trunk VLAN pruning, DAI trust only on trunks, per-port storm control and disabled unused ports (live status); on the MX IP source guard, intrusion prevention, AMP, appliance services blocked from the WAN, port forwarding and 1:1 NAT restricted to known sources, logged default firewall rule and content filtering; per SSID (each enabled SSID is its own target) no open auth, WPA2 or stronger, 802.1X with redundant RADIUS servers on corporate SSIDs, 802.11w, a splash page on open SSIDs, and on guest SSIDs LAN isolation (NAT mode, LAN isolation or the SSID firewall's *Wireless clients accessing LAN* rule, read per SSID), mandatory DHCP and a per-client bandwidth cap; per network syslog, SNMPv3-or-off and alert destinations; and for the organization two-factor authentication on every administrator and enforced, strong passwords, idle timeout, lockout, password expiration and reuse, dormant administrators, API key IP restriction and SNMPv3-only polling (46 checks, each with parameters such as exempt port tags or the guest SSID name pattern). Rules are evaluated by a **Meraki scan** of an organization registered on the Topology page, with its stored API key, read-only and rate-limited like a topology collection, reading only the endpoints the profile's checks need; host (SSH) scans skip Meraki rules and Meraki scans skip config rules, so one profile can hold both. A scan runs as a background job and stores one result per *target* - the organization, each network (only the checks whose product it has), each switch and each enabled SSID - with per-check findings and evidence (the offending ports, SSIDs, rules, administrators); a payload the key cannot read is reported as *unreadable* (status `error`), never as compliant or as a violation, and a 400/404 means not applicable. Four built-in profiles (**Load Built-in**): **Meraki Switch Security Baseline**, **Meraki Security Appliance Baseline**, **Meraki Wireless Security Baseline**, **Meraki Dashboard Access Hardening**; the demo organization (**Load Sample → Meraki**) can be scanned without a key. The Compliance page gains a **Meraki** tab (assignments of a profile to organizations on a schedule with **Scan Now** and live progress, **Target Status** per organization / network / switch / SSID, **Scan Results**, read-only findings with evidence), **Run Scan → Meraki Organization**, an **Add a Meraki check** picker in the profile editor that inserts the rule JSON, and Meraki counts in the summary strip. Scheduled Meraki assignments run from the existing compliance scheduler with the same retention. Profile create/update rejects an unknown Meraki check. New routes `/api/compliance/meraki/*` (checks catalog, orgs, assignments, scan / scan-now jobs, results, status, summary) and tables `meraki_compliance_assignments`, `meraki_compliance_results` (migration 0068). There is no remediation for Meraki findings: Plexus never writes to the Dashboard API. Guide: `docs/meraki-compliance.md`.

### Software
- Add a **Software** page (**Network → Software**, feature `software` / `software.write`) that tracks the software version of every device Plexus knows and alerts on vulnerable ones. The tracked set is built from inventory hosts (the version SNMP/SSH stored) and the devices of the latest topology collection of every Meraki organization (firmware per device), Cato account (Socket version) and AnyConnect FMC (FTD software, FMC version), each classified to a platform (Cisco IOS / IOS XE / IOS XR / NX-OS / ASA / FTD / FMC, Meraki MX / MS / MR / MG / MV / MT, Cato Socket, Junos, EOS, FortiOS, PAN-OS); a topology device that is an inventory host is listed once. Versions compare by their parts (`17.9.4a` > `17.9.4`, `15.2(7)E10` > `15.2(7)E8`), so **Version Spread** shows per platform how many devices run each version, the newest in the fleet and how many are behind it (**behind** badge); every rebuild records version changes with the previous version (**Recent Version Changes**, per-device **History**). **Advisories** are checked against every device: entered by hand or imported as JSON with a version specification grammar (exact, `17.9.*`, `<17.6.5`, `17.3..17.6.4`, comma-joined constraints, platform and model filters), or synced from **Cisco PSIRT openVuln** (admin; client ID and secret stored encrypted and write-only; one paced query per distinct tracked IOS/IOS XE/IOS XR/NX-OS/ASA/FTD/FMC/FXOS version, advisories stored with Cisco's severity, CVSS, CVEs, first fixed and URL; manual **Sync** as a background job or on a schedule). A device on an affected version opens a **Vulnerability Alert** (acknowledge; resolved when it no longer matches, reopened unacknowledged on a downgrade); new alerts at or above a configurable severity floor are sent to the notification channels as `software_vulnerability` alerts. The set is rebuilt every six hours (configurable), after every topology collection, and on **Refresh**. New `/api/software/*` routes and tables `software_versions`, `software_version_history`, `software_advisories`, `software_alerts`, `software_settings` (migration 0067). Guide: `docs/software-versions.md`.

### Topology
- Draw like devices alike on the Topology map. A VPC or VNet peered from an account or subscription Plexus does not collect is now a VPC node in a box of its own (`vpc-… (not collected)`), like the peered VPCs that are collected, instead of a gateway hexagon in the transit box; it is not counted as a device or site. In the default tidy layout a device with links into other sites (a VPN hub, a VPC peered with many others) now sits level with its own site's devices, so its site box is drawn instead of being dropped, and a site whose devices are placed in several spots (the AWS transit and VPN box) is framed in each spot instead of not at all. An appliance's WAN uplinks (and a VPC's internet gateway) are now drawn just above it in its column instead of under all of its other links, where a site with a large switch and access point tree put them a screen away from the appliance.
- Show what is known about a peered AWS VPC that Plexus does not collect. Its peering records its CIDR ranges, region and account number, so the node now shows them (model `AWS VPC 10.7.1.0/24 (not collected)`, box `vpc-… (us-east-2, not collected)`), says why it is not collected (account not in Cloud Visibility, region not among the account's regions, or not discovered yet) and lists its peerings and the routes of the collected VPCs that lead to it (**Routing** tab). Every collected VPC now lists its peerings (**VPC peerings**, Routing tab). The collector also records each peered VPC's secondary and IPv6 ranges; run **Discover** again to see them.
- Narrow the Topology map to one integration. The source selector now offers **All integrations** (the former **Meraki only**) and a **Meraki only**, **Cato only**, **AnyConnect only** and **AWS only** choice for each integration on the map; a single integration keeps its own devices and the links between them. Links from integrations now carry their `provider` in `/api/topology`'s TypeScript type (the API already sent it).
- Give the HTML map export the same source selector. The file still holds every source; picking **AWS only** (or **Inventory only**, **All integrations**, any one integration) shows that part, packs its sites together, recounts the header and limits search and Path to it. Exported devices and links now carry their `provider` (and devices `integration_only`) for it.
- One **Sources** button on the Topology toolbar replaces **Discover Neighbors** and **Meraki / Cato**. Its dialog lists everything that feeds the map in one table - CDP/LLDP neighbor discovery of the inventory, Meraki organizations, Cato accounts and the AWS accounts of Cloud Visibility - each with its last collection, status, warnings and a **Collect Now** button; **Collect All** refreshes every source the user may collect from, **Add Source** and **Load Sample** ask for the type first. AWS accounts are still managed under Cloud Visibility (the row links there, and discovery stays an administrator action); an AWS account that is on the map now says so on the Cloud Visibility accounts table. New `GET /api/topology/sources` returns the list (no credentials). The empty map offers the same dialog.
- Add Meraki support to the Topology map. Register a Meraki organization from the Topology toolbar (**Meraki**; Dashboard API key stored encrypted, write-only) and collect on demand: a rate-limited, read-only Dashboard API v1 collector gathers networks, devices, status, link-layer topology, LLDP/CDP, WAN uplinks, AutoVPN and non-Meraki VPN peers, VLANs, static routes, BGP/OSPF, switch ports and SVIs, firewall/NAT rules and SSIDs, with secrets (PSKs, IPsec/RADIUS secrets) scrubbed at collection. The latest collection of each organization is merged into `/api/topology` (all-groups view): Meraki devices, WAN uplinks and VPN tunnels join the existing graph as framed, pre-arranged sites, and a Meraki device or LLDP/CDP neighbor that is also an inventory host collapses into that host's node. Node details gain one tab per category of collected Meraki data (Device, Interfaces, VLANs, MAC/ARP, Routing, VPN, Firewall, Switching, Wireless), shown only when there is data for it; the toolbar search now also searches collected Meraki detail and can highlight every match on the map; a source filter narrows the map to inventory or Meraki. New **HTML** export renders the whole topology (inventory and Meraki, with collected interfaces, VLANs, neighbors and routes embedded) as one self-contained interactive file for sharing. Optional live SSH show commands (service credential) enrich inventory-matched nodes at collection time. The map now opens in a new default **Tidy tree** layout (left-to-right trees, one row per device, no physics) so it is readable without arranging anything; the previous layouts remain selectable. Large maps stay usable: sites are arranged in columns instead of one tall strip, VPN tunnels beyond 300 are drawn per selected device (toolbar **VPN Tunnels** draws all), and maps over ~600 devices drop glows (links stay drawn while panning and zooming); the HTML export draws tunnels over the site boxes (under the devices) and applies the same 300-tunnel rule. **Path Mode** now takes up to six devices, Meraki sites or subnets (picked from a list or typed as an IP address/network; a subnet stands for the appliance, L3 switch or non-Meraki VPN peer that owns it) and traces every pair hop by hop over the links that are up, warning when a tunnel on the path will not carry a picked subnet (also in the HTML export, as **Path**; new `GET /api/meraki/subnets`). MAC/ARP is filled from a per-network client collection (MAC, IP, VLAN, port, SSID; last 24 hours; option **Clients (MAC / IP)**, on by default). Collections run as background jobs with progress; a bundled sample organization previews the feature without an API key. New tables `meraki_orgs` / `meraki_topology_snapshots` (migration 0064). Guide: `docs/meraki-topology.md`.
- Show the subnets of the Topology collections on the IPAM page and find the ranges two sites both hold. `GET /api/ipam/overview` now adds the subnet index of the latest snapshot of every Meraki organization (VLANs, single LANs, switch SVIs, static routes), Cato account (network ranges) and AnyConnect FMC (address pools) as source `topology` (`include_topology=false` leaves them out; AWS is not listed twice, its VPCs and subnets stay cloud resources), with the sites that hold each subnet (`topology_sites_preview`, `topology_providers`) and Meraki/Cato VLAN IDs merged into `vlan_ids`. New `overlaps`: pairs of ranges held by two different owners (sites, or a site and a VPC/VNet) that are the same network or one inside the other, found by one sweep over the address space, with both sides, the relation and `vpn_conflict` when both sides are advertised into a VPN (the AutoVPN problem of two branches on the same user VLAN); `summary.overlap_count` / `vpn_overlap_count`, per-subnet `overlap_count`, first 500 pairs returned, VPN conflicts first. Static routes and subnets behind VPN peers are listed but not checked, and a range a site lists twice (VLAN and SVI) is not a pair. The IPAM page gains **Include Topology Subnets**, **Topology Subnets** and **Overlapping Ranges** summary cards (red when a VPN conflict exists), an **Overlapping Ranges** card, an overlap badge on subnet rows and a **Sites:** preview. The overview also now returns what the page was already rendering: cloud resource names (`cloud_resource_names_preview`, previously only a distinct CIDR count), `version`, `prefix_length`, `total_addresses`, and `allocated` / `reserved` / `available_address_count` (reservations counted), so the Subnet Inventory table no longer shows every subnet as 0 addresses with 0 available.
- Add Cisco AnyConnect remote access VPN to the Topology map, read from the FMC that manages the FTD headends. An FMC is registered from the **Sources** dialog (**Add Source → AnyConnect (FMC)**; `POST /api/meraki/orgs` with `provider: "anyconnect"`, the FMC address as `base_url`, the domain as `org_id`, the API username in `options` and the password as the write-only `api_key`, stored encrypted; `https` host only, redirects never followed, optional `verify_tls`) and collected on demand by a read-only, paced FMC REST client (token login, one sign-in per collection, retried on rate limit, 120 requests per minute respected): device records, remote access VPN policies and their policy assignments, connection profiles, address assignment and access interface settings, IPv4 address pools, the physical and sub-interfaces of each headend, and the connected sessions from `health/ravpnsessions` (FMC 7.3+, best-effort). Every FTD with a remote access VPN policy is drawn as a site box holding the device (health as the border), a WAN stub per access interface with the interface's address, and one **AnyConnect users (N)** node listing the connected users (assigned IP, public IP, profile, group policy, client, OS, login time); the policy's address pools are the site's **VPN address pools**, so they can be picked in Path Mode and are found by search. The FMC is one node in its own box, joined to each headend by a dotted **Managed by FMC** link (new edge protocol `management`) that Path Mode, the tidy-tree layout and the HTML export's path finder ignore. An FTDv in AWS is matched to its instance by the private address of its access interface, like a vMX behind a NAT gateway, when its FMC model is virtual; a headend that is an inventory host becomes that host. **Test Login** signs in and lists the domains the user can see; **Load Sample → AnyConnect** adds a demo FMC whose two headends are the FTDv instances of the demo AWS account. Guide: `docs/anyconnect-topology.md`.
- Add Cato Networks to the Topology map. A Cato account is registered from the same toolbar dialog as a Meraki organization (now **Meraki / Cato**; `POST /api/meraki/orgs` with `provider: "cato"`, account ID and API key, key stored encrypted and write-only, API host restricted to `catonetworks.com`) and collected on demand by a read-only, paced GraphQL client: `accountSnapshot` for sites, Sockets, WAN links, PoPs, HA state and connected remote users, and `entityLookup` for the network ranges of every site. The result uses the Meraki snapshot format, so it is merged into `/api/topology` and covered by node details, deep search, Path Mode (sites and subnets; paths run Socket → PoP → Cato Cloud → PoP → Socket) and the HTML export with no separate code path: each site is a framed box with its Socket(s) and WAN links, the PoPs in use and a backbone node form a **Cato Cloud** box, and connected remote users are one node with the users listed and searchable behind it. New `meraki_orgs.provider` column (migration 0066); `POST /api/meraki/sample?provider=cato` adds a demo account. Guide: `docs/cato-topology.md`.
- Add AWS to the Topology map. Every enabled AWS account that Cloud Visibility has discovered is built into one snapshot in the Meraki snapshot format and merged into `/api/topology`, so it is covered by node details, deep search, Path Mode and the HTML export with no separate code path, and follows each new discovery (manual or scheduled). Each VPC is a framed site whose router node owns the VPC's subnets, with its internet, NAT and virtual private gateways; transit gateways, Direct Connect and customer gateways form an **AWS transit and VPN** box; attachments and peerings are a new link type (`protocol: "cloud"`), and a site-to-site VPN is a tunnel that is down only when all of its tunnels are. Instances are nodes only when they forward traffic (source/destination check off) or are inventory hosts; the rest are listed and searchable in their VPC. The AWS collector additionally reads subnets, instances with their interfaces, customer gateways, VPN tunnel status, route table routes and Direct Connect virtual interfaces and gateways; these map sections are best-effort (a denied call is recorded as a `collection_warning` resource and reported, not fatal), and VPN pre-shared keys are never read. Snapshots of different integrations are now joined by public IP address: a customer gateway or non-Meraki VPN peer becomes the device that answers on its address, a cloud instance becomes the Meraki or Cato virtual appliance on its public IP, and a VPN seen from both ends is one link. Path Mode can pick VPCs and their subnets. `POST /api/meraki/sample?provider=aws` (**Load AWS Sample**) adds a demo AWS account; the AWS sample discovery is now three VPCs with a transit gateway, a firewall pair, a VPN and a Direct Connect. The AWS account form explains how discovery signs in. Guide: `docs/aws-topology.md`.
- Check AWS routing and filtering in Path Mode. For a pair of subnets or IP addresses with an end in a VPC, Plexus now decides whether AWS carries and permits the flow, in both directions, and shows the verdict (**allows it**, **blocks it**, **allows part of it**, **check incomplete**) with every step under the path: the subnet's route table (longest prefix, blackhole routes), VPC peerings (active, and only between their two VPCs), the transit gateway route table associated with the arriving attachment (on to a VPC, a VPN that has a tunnel up, Direct Connect or a peered transit gateway), the stateless network ACLs of both subnets for the request and for the reply on the ephemeral ports, and the security groups of an instance when an end is typed as its IP address, including rules that name another group. A new **Traffic** box takes `tcp/443`, `udp/53`, `icmp` or nothing for any traffic. An end outside AWS is followed to the gateway it leaves by and back in. Nothing unchecked is reported as allowed: a route to a firewall instance, an inspection VPC, a prefix list, or data a discovery did not collect gives *check incomplete* with the reason. The AWS collector additionally reads network ACLs, transit gateway route tables with their routes, the route table of each transit gateway attachment and the security group IDs of instances and their interfaces (best-effort sections; new permissions `ec2:DescribeNetworkAcls`, `ec2:DescribeTransitGatewayRouteTables`, `ec2:SearchTransitGatewayRoutes`; run **Discover** again to collect them). VPC details list the network ACL rules and each subnet's ACL, a transit gateway lists its routes, and the AWS sample gains ACLs, security groups and a transit gateway route table. New `GET /api/meraki/aws/reachability`; `GET /api/meraki/subnets` entries carry `provider`.
- Run the AWS / Azure check of a path in more cases, and say why when it does not run. An IP address typed into the subnet box that falls in a range of a Cato vSocket or Meraki vMX running in AWS (a vSocket's ranges are subnets of its VPC too) resolved to the Cato or Meraki range, and no AWS check ran; the check now runs whenever an end's device is also an AWS or Azure instance. A check that finds neither address in a collected VPC now says so instead of showing nothing. A leg with an end in a VPC or VNet whose other end was picked as a device or site (a Meraki appliance clicked on the map) used to show only "route tables are not consulted"; it now says which end to add with the subnet box (one of its subnets or an IP address) so the cloud's route tables and rules are checked. The note under a path now says the drawn path shows how the ends are joined rather than the route each device picks, and the HTML export says it draws the path only and does not run the cloud check.
- Recognise a Meraki vMX that sits behind a NAT gateway, and check paths through a vMX. An instance in a private subnet has no public IP for the public-address match, so it is now also matched by the private IP of the appliance's WAN uplink when that is unambiguous: the instance forwards traffic, one instance and one uplink have the address, and either the Meraki model is a vMX or the public IP Meraki reports is a NAT gateway of the instance's VPC. The match no longer depends on the order snapshots are merged in. In the AWS check of a path, a route that hands traffic to an instance that is a Meraki appliance no longer ends in *check incomplete*: the latest Meraki collection decides whether an AutoVPN tunnel that is up joins the vMX to the site owning the far subnet, whether that site advertises the subnet, and whether the vMX advertises the AWS address back; the reply is followed from the vMX's subnet. Meraki firewall rules are not matched.
- Track the MAC addresses seen on Meraki devices in MAC tracking. Each Meraki collection upserts its clients (MAC, IP, VLAN, port or SSID, client name, manufacturer, device last seen on) into the new `meraki_clients` table (migration 0065), keeping first-seen/last-seen across collections, so a client stays searchable after it leaves Meraki's one-day window or its snapshot is deleted. `GET /api/mac-tracking/search` now returns these alongside inventory forwarding-table entries (`source: "meraki"`, also matched by client or device name), `GET /api/mac-tracking/stats` counts them (`meraki_clients`, `meraki_devices`), and `POST /api/mac-tracking/cleanup` prunes them. The MAC / ARP Tracking page marks Meraki clients and shows their network; **Find MAC/IP/VLAN** on the Topology page highlights the Meraki device a client was seen on. Meraki clients have no move history.
