# Changelog

## Unreleased

- OPNsense is a platform of its own in the inventory (`docs/opnsense-topology.md#config-backup`): the host dialog's **Platform** list has **OPNsense firewall (API and SNMP, no SSH)**, and each OPNsense source collection sets the platform of the inventory host it matches to the firewall. A firewall added by hand with another platform was backed up over SSH and needed a credential; it is now backed up over the source's API like an imported one. The firewall's **Inventory platform** section and the host's change history record the change.
- Config drift snapshots of OPNsense firewalls no longer ask for an SSH credential (`docs/config-backups-and-drift.md#capture-a-snapshot`): **Capture Snapshot** has a **None (OPNsense firewalls only)** choice, and `credential_id` is optional on the capture and check endpoints. An OPNsense snapshot was always taken from the firewall's newest config.xml backup, but a credential had to be picked anyway. Without a credential, any other host fails with a message that it needs one.
- Custom SNMP trap rules (`docs/snmp-traps.md`, migration 0138): under Monitoring > Configure > Syslog Rules, **SNMP trap rules** now takes your own rules next to the built-in ones. A rule names the traps that raise it (a trap OID, an OID prefix ending in `.*`, or a registry name), up to ten varbind conditions (equals, contains or a regular expression), the varbind that names the instance, and optionally the traps that clear it; severity, threshold and auto-resolve work as on a custom syslog rule. A trap the registry does not name can now raise an alert through a custom rule. Alerts have type `trap` and metric `trap_custom_<id>`; disabling or deleting a rule resolves its open alerts. **Test** shows what the rules do with a stored trap or with an OID and varbinds you type. API: `POST`, `PUT /{id}`, `DELETE /{id}` and `POST /test` under `/api/monitoring/trap-rules` (`monitoring.write`, audited as `trap_rule.*`).
- A CISCO-SYSLOG-MIB `clogMessageGenerated` trap is matched by the syslog rules (`docs/snmp-traps.md`, `docs/syslog-rules.md`): the syslog line the trap carries (`%FACILITY-SEVERITY-MNEMONIC: text`) goes through the built-in and custom syslog rules and the re-poll and config-change triggers, under the same alert key as the same message received as syslog, so a device that sends both raises one alert. It follows the syslog switches (`syslog_alerts`), not `trap_alerts`.
- HA and redundancy state is polled (`docs/monitoring.md#ha-and-redundancy-state`, `docs/vendor-monitoring-coverage.md`): the monitoring poll reads Cisco ASA / FTD failover, Cisco supervisor redundancy and StackWise members, ring and stack ports, Juniper Routing Engine redundancy and Virtual Chassis ports, FortiGate HA, PAN-OS HA, AOS-CX VSF and VSX, and VRRP and HSRP groups, and raises `ha_peer_down` (critical), `ha_link_down` and `fhrp_group_down` (warning), one alert per unit, link or group, resolved when the state recovers. A change of the active role raises `ha_role_change` (warning, resolved an hour after the last change). The gaps (Arista MLAG, Juniper SRX chassis cluster and others) are listed in the coverage document.
- Device restarts are told from the polled uptime (`docs/monitoring.md#device-restarts`): an uptime that went back, or that shows the device came up since the previous poll, raises `device_restarted` (warning, one per host, resolved an hour after the last restart) and marks the host's hardware inventory for a re-read. A wrap of the 32-bit sysUpTime counter (about 497 days) is not a restart. This catches a reboot faster than the ICMP down threshold from a device that sends neither a trap nor a syslog message.
- SNMPv3 informs are authenticated, decoded and answered (`docs/snmp-traps.md`, migration 0139): the trap receiver is now an SNMPv3 authoritative engine with its own engine ID and a boots counter kept across restarts. An inform from an inventory host is checked with that host's SNMPv3 poll user, acted on like a trap, and acknowledged at the same security level; engine discovery and an out-of-window message are answered with the Report the standard asks for, and nothing is sent for an unknown user, a wrong digest or a decryption failure. The engine ID and the counters are in `GET /api/admin/metrics/receivers/config`.
- Trap receiver state survives a restart (`docs/snmp-traps.md`, `DATA_RETENTION.md`): the SNMPv3 replay record is stored (at most once a minute and at shutdown) and read back at startup, and the threshold counters of the trap rules are rebuilt from the stored SNMPv1 / v2c traps as the syslog counters are.
- SNMP over IPv6 (`docs/administration.md`, `deploy/FIREWALL.md`): a host with an IPv6 address is polled over IPv6, and the trap receiver also listens on IPv6, on the same port. Addresses with a zone (link-local scope) are not accepted. Syslog listeners are unchanged (IPv4). Upgrade guidance: a trap reaches the container over IPv6 only when the compose network has IPv6; where it does, filter the trap port with `ip6tables` as you do for IPv4.
- Secret variables have a **Usable by** rule (`docs/jobs.md#who-may-use-a-secret-variable`, migration 0140): an admin can limit a secret to admins only or to the members of chosen access groups, from the create and edit form under Credentials > Secret Variables; the list shows each rule. A job may use the secret only when the rule includes the person who launched it: launch, retry and **Run Live** check the caller, and the queue checks the launcher again before the job signs in. A secret the rule does not allow is reported exactly like one that does not exist. Admins and the server API token are always allowed; SNMP polling is not affected. API: `usable_by: {roles, groups}` on `POST` and `PUT /api/secret-variables` and in the list and get answers.
- Upgrade guidance: existing secret variables stay usable by every user who can run jobs until an admin restricts them under **Usable by**.
- Optics and PoE are polled (`docs/monitoring.md`, `docs/vendor-monitoring-coverage.md`): the monitoring poll reads transceiver receive and transmit light levels against the device's own thresholds (Cisco CISCO-ENTITY-SENSOR-MIB dBm sensors, Juniper JUNIPER-DOM-MIB, Arista and PAN-OS ENTITY-STATE-MIB, AOS-Switch HP-ICF-TRANSCEIVER-MIB) and raises `optic_level_alarm`, warning or critical as the device says, one alert per optic. An optic on a port an operator shut down is not an alert, and one on a port whose link is down raises none (the interface check reports the link). POWER-ETHERNET-MIB is read into `poe_port_fault` (warning), `poe_supply_down` (critical) and `poe_budget_high` (warning, at the device's own usage threshold, else 90%). Optics on FortiOS, AOS-CX and Netgear are a documented gap.
- EIGRP, IS-IS and IP SLA are polled, and Cisco BGP peers inside VRFs (`docs/monitoring.md`): `eigrp_neighbor_down` and `isis_adjacency_down` (critical; a neighbor down or gone at two polls in a row), `ip_sla_down` (critical, warning for over threshold) and, for BGP, CISCO-BGP4-MIB `cbgpPeer3Table`, which shows the peers of every VRF without an SNMP context (the alert names the VRF). IPsec tunnels stay a documented gap: the flow monitor MIB lists active tunnels only. Upgrade guidance: on a Cisco device that answers `cbgpPeer3Table`, an open `bgp_peer_down` alert resolves once and is raised again under the new key, so a peer that is down at the upgrade notifies once more.
- Syslog rules for temperature, HA failover and device restarts (`docs/syslog-rules.md`): three new built-in rules, `syslog_temperature` (critical), `syslog_ha_switchover` and `syslog_device_restart` (warning), with the severity, auto-resolve time and re-poll of the trap rules of the same names, so the event alerts whether the device sends syslog or traps. They cover Cisco IOS XE, classic IOS, Catalyst 4500, NX-OS, IOS XR, ASA and FTD, Arista EOS, Junos, FortiOS, PAN-OS and HPE Aruba, from each vendor's message reference. A Cisco ASA or FTD failover now raises an alert, and a syslog-only device that reboots raises one even when the ping never sees it down. Upgrade guidance: a planned reload raises `syslog_device_restart` too (warning, resolved after 60 minutes); switch the rule off or suppress it for maintenance windows if that is too much.
- Syslog rules: vendor forms added (`docs/syslog-rules.md`, `docs/vendor-monitoring-coverage.md`). Cisco FTD messages (`%FTD-`) match the interface, login failure, configuration change and restart forms. New module down forms for the Catalyst 4500, IOS XR, Arista EOS, FortiGate, AOS-CX and AOS-Switch; IOS XR power supply and fan forms; ASA / FTD fan and power supply messages (`735001` to `735006`, `735011`, `735012`); Catalyst 9000 system fan failure and recovery. The **Related** hint of Received messages recognises temperature, HA and restart messages. The forms no reference could be retrieved for are listed under Known gaps.
- Event rule packs for layer 2, neighbors and device health (`docs/syslog-rules.md`, `docs/snmp-traps.md`): 20 new built-in syslog rules for Cisco IOS / IOS XE (EIGRP, IS-IS and service crashes on NX-OS too) and 11 trap rules for the same events. Layer 2: spanning tree root and topology changes (BRIDGE-MIB `newRoot` and `topologyChange` now raise alerts), root guard, loop guard and Bridge Assurance blocking, err-disabled ports, port security violations, storm control, MAC flapping, duplex mismatch. Neighbors: HSRP failover, EIGRP and IS-IS neighbors, IPsec sessions, IP SLA tracking. Device health: PoE faults, optic light levels, RADIUS server dead, NTP sync lost, license and certificate expiry, memory allocation failures and crashes. Noisy events are threshold rules (five topology changes or three MAC moves in ten minutes); events with no clearing message resolve on a timer. Every rule can be switched off or given another severity under Monitoring > Configure > Syslog Rules. The vendors and events with no confirmed message form are listed under Known gaps.
- Config backups: **Run Now** says why a host failed. The message used to give only the counts (`0 saved, 1 errors`), with the reason on the host's `error` entry under **History**; it now lists the first five failed hosts with their reason (an OPNsense firewall that is not the firewall of any collected source, a source without an API key, a refused `config.xml` download, a policy without a credential for an SSH host). `POST /api/config-backups/policies/{id}/run-now` returns them as `failures` (`host_id`, `hostname`, `ip_address`, `error`; 25 at most) next to the counts (`docs/config-backups-and-drift.md`).
- Security: ongoing hardening of authentication, authorization, credential handling, input validation and resource limits. Detailed findings and remediation tracking are maintained privately; this does not mean all findings are resolved. Deployment limitations and configuration guidance remain in the administration guides.
- Upgrade guidance: password sign-in now follows the saved **Auth Provider**. Before this release a RADIUS, TACACS+ or LDAP provider saved under Settings > Authentication was not applied to password sign-in, which checked local accounts only. After the upgrade a deployment with one of those providers saved sends password sign-ins to that server: check the provider, its server settings and its local fallback before upgrading, and keep at least one admin account that was created in Plexus (`docs/administration.md`). Deployments with the provider **Local**, and OIDC and SAML sign-in, are unchanged.
- Upgrade guidance: a local password is accepted only for an account whose provider is Local. An account that RADIUS, TACACS+, LDAP, OIDC or SAML manages no longer signs in with a password Plexus holds, on any path and whatever its role, so an admin account created by a directory or SSO sign-in is not a break-glass account. Changing an account's provider clears its local password (an account set back to `local` needs **Reset password**), an admin cannot set a password on a managed account (`400`), and such an account's own change-password is refused. `scripts/reset_admin_password.py` run for a managed account makes it local. Wrong current passwords on the change-password form are limited per account, also for requests sent together.
- Upgrade guidance: a single sign-on callback that fails before it is tied to a sign-in started in this browser (no transaction, a state that does not match, a SAML response that does not validate) no longer counts toward the login lockout of the client address, and a refused callback from a locked-out address is logged without an audit entry; failures after that point count as before (`docs/sso-oidc.md`, `docs/sso-saml.md`). Saving the login rules or the authentication settings is now audited (`auth` / `login_rules.update`, `auth_config.update`) with what changed.
- Upgrade guidance: sign-in answers and limits. A failed password sign-in is told "Invalid username or password", or "Sign-in is temporarily unavailable" when a RADIUS, TACACS+ or LDAP server does not answer; which server and why is in the `auth` / `login.failure` audit entry and the server log. The lock message now says it is on the client address. One address can have at most **Max attempts** password sign-ins in progress and the server checks at most 16 passwords at once (`429` past either, not counted as a failure); self-registration counts against the anonymous API write limit; `deploy/nginx.conf` adds a request rate for `/api/auth/login` and `/api/auth/register` (30 a minute per address, burst 20): copy the new `limit_req_zone` line and `location` block into a customized config, and raise the numbers where many users share one address. The sign-in name is at most 256 characters, and audit text is stored on one line (`docs/administration.md#authentication`).
- Upgrade guidance: account names and passwords (`docs/administration.md`, "Password rules" and "Username rules"). A new or renamed account cannot take a name that differs from an existing one only in case, cannot be named `api-token` (the name the server API token acts under; an external sign-in under it is refused), and a new password is 8 to 256 characters and not the username. Existing accounts and passwords keep working. Display names are limited to 200 characters on one line and a self-service change is audited (`auth` / `profile.update`). **Session never expires** can no longer be turned on for an admin account, or an account with it be made admin; accounts that already have both keep them until changed. `POST /api/admin/users` and `PUT /api/admin/users/{id}/password` accept `must_change_password`.
- Upgrade guidance: OIDC (`docs/sso-oidc.md`). With **Username Claim** `email`, the ID token must now carry `email_verified: true`; a provider that never sends the claim (Entra ID) fails with the `claims` error until **Allow unverified email** is turned on or another username claim is used. Sign in with a local admin to change it. A token that names several audiences must carry `azp`. When the provider changes a person's username, they now sign in to the account bound to their subject instead of getting a second account (`auth` / `login.sso_username_changed`); the same holds for SAML.
- Upgrade guidance: SAML (`docs/sso-saml.md`). An attribute setting is matched against the attributes' `Name` first; a `FriendlyName` is used only when no attribute has that `Name`, so check the mapping if two attributes of your IdP share a label. New optional settings: **Subject Attribute** (bind the account to a stable attribute; set it when the NameID is transient) and **Required Authentication Context** (ask the IdP for, and require, for example a multi-factor context).
- Upgrade guidance: LDAP **Username Attribute** (`docs/administration.md#authentication`), empty by default (accounts keep the name as typed). Set it (`sAMAccountName`, `uid`) when the user search filter accepts more than one form of a name, so one person gets one account; people who used to type another form then get a new account, so move their access groups. The security check (`GET /api/admin/security-check`) now also warns about RADIUS without Message-Authenticator enforcement, LDAP without TLS or with weak certificate checking, such a filter without the attribute, OIDC with unverified email, a provider whose default role is `admin`, and a session cookie without `Secure`, and reports the flag the cookie really carries.
- Accounts can be disabled without deleting them (`docs/administration.md`, migration 0137): **Account disabled** in **Edit User Account** (`PUT /api/admin/users/{id}` with `disabled`) blocks every sign-in for the account (local, RADIUS, TACACS+, LDAP, OIDC, SAML), ends its open sessions and stops the AI-access tokens it owns; the user card shows **Disabled**. Upgrade guidance: existing accounts stay enabled. An external sign-in is checked against its provider only when the person signs in, so disable (or delete) the Plexus account of someone removed at the directory or IdP. The last enabled admin cannot be disabled, demoted or deleted, and a disabled admin does not count as one.
- Upgrade guidance: the development sign-in (`APP_ENV=dev` or `PLEXUS_DEV_BOOTSTRAP`) no longer applies to an account a sign-in provider manages, and logs a warning each time it is used. Never enable it outside development.
- Upgrade guidance: hosts that exist at the upgrade count as confirmed. From then on a host added or re-addressed by a non-admin (single or bulk add, bulk import, discovery sync or onboard, an IP edit) and a host a scheduled sync job adds show **Awaiting admin confirmation** on the Inventory page and are not polled or collected with shared secrets until an admin confirms them there (or `POST /api/admin/hosts/confirm-address`). A waiting host is never shown as down and raises no availability or SLA alert. Monitoring and MAC tracking no longer fall back to a default credential that is not a service credential. An upgrade campaign or deployment that runs with the service or default credential signs in only to hosts with a confirmed address, whoever runs it: a deployment with a waiting host is refused (`409`) before any device is touched, a rollback skips that host, and a campaign fails that device for the phase and carries on with the others, as it does for a device whose inventory host was re-addressed or deleted since it was added (`docs/deployments.md`, `docs/upgrade-tool-guide.md`, migration 0135). A discovery scan or sync by a non-admin probes addresses that are not confirmed inventory hosts without SNMP and says so in the result (`snmp_withheld`, `docs/discovery.md`); an admin's scan and the scheduled sync are unchanged.
- Upgrade guidance: `deploy/nginx.conf` now allows 100 connections with a request in progress per client address (`limit_conn`, `429` past it); raise the number where many users share one NAT address.
- Upgrade guidance: an LDAP, RADIUS or TACACS+ sign-in is matched to the provider's existing account without regard to case, so `ALICE` signs in to `alice` instead of becoming a second account, and four-eyes approval compares names the same way; accounts that already differ only in case keep signing in with their exact spelling and should be merged by hand (`docs/administration.md`). With LDAP direct bind and a UPN domain derived from the base DN, a sign-in name containing `@` or `\` is refused: users type the plain account name. A browser client served from another host than Plexus needs its origin in `APP_CORS_ORIGINS` to open the job sockets. The break-glass local admin path is now documented with what it bypasses and how to turn it off (`PLEXUS_BREAKGLASS_LOCAL_ADMIN`).
- Account disabled (`docs/administration.md`): an admin can switch a user account off without deleting it, with **Account disabled** in **Edit User Account** or `PUT /api/admin/users/{id}` with `{"disabled": true}`; the user list shows **Disabled** and `GET /api/admin/users` returns `disabled`. A disabled account cannot sign in by any method (password, break-glass, RADIUS, TACACS+, LDAP, OIDC, SAML): it gets the answer a wrong password gets and the attempt is audited as `auth` / `login.failure` with "account disabled". Its open sessions end at once and stay ended after it is re-enabled, the AI-access (MCP) tokens it owns are refused, and a directory or IdP sign-in never re-enables or changes it. Use it to cut off a person removed at the directory or identity provider, whose session and tokens otherwise keep working until the account is deleted. An admin cannot disable their own account, and the last enabled admin cannot be disabled, demoted or deleted (a disabled admin no longer counts as one). The change is listed in the `auth` / `user.update` audit entry. Upgrade guidance: migration 0137 adds the `users.disabled` column; no action is needed and existing accounts stay enabled.
- Hardware inventory with history (`docs/hardware-inventory.md`): every hardware component with a serial on an inventory host (chassis, stack members, supervisors, line cards and other modules, power supplies, fan trays, transceivers) is now kept per host, with a history of when a component was replaced (old and new serial), installed (with the host it was last seen on), removed, moved to another slot or changed model or revision. The monitoring poll reads it over SNMP (ENTITY-MIB `entPhysicalTable` for every SNMP-polled device type; JUNIPER-MIB `jnxContentsTable` first on Junos) at most every 6 hours, sooner after a module or restart syslog message or trap, and **Refresh hardware** on the device page's new **Hardware** tab reads it now. **Fetch serial** also runs `show inventory` on Cisco IOS, IOS XE, NX-OS, IOS XR, ASA and FTD hosts and stores the components. A component is removed only when a complete read still lacks it after it has been missing for 30 minutes (a swap slower than that is still recorded as a replacement), and a read that lists nothing is believed only after three in a row. SNMP and SSH do not take turns on a host: a host with a recent SNMP read keeps SNMP as its source. A new **Hardware** page (sidebar, after Inventory) lists every component across devices (search by serial, model, slot or host, CSV export) and every change. The host serial is filled from the chassis only when empty. The history is not pruned automatically (`DATA_RETENTION.md`). Placeholder serials ("N/A", zeros) read by discovery are now treated as no serial. Not confirmed against a live device; other vendors' SSH inventory commands are not read (`docs/vendor-monitoring-coverage.md`).
- Module down alerts (`docs/syslog-rules.md`, `docs/monitoring.md#hardware-module-health`): a line card, supervisor, sub-module or stack member that fails, goes offline, loses power or is removed now raises an alert two ways. A new built-in syslog rule, **Module down** (`syslog_module`, critical, on by default), matches the messages of Cisco IOS XE (`IOSXE_OIR`, `SPA_OIR`), Catalyst 3750 / 2975 stacks (`STACKMGR`), Catalyst 6500 (`C6KPWR`), NX-OS (`MODULE`, `PLATFORM`) and Juniper Junos (`CHASSISD_SNMP_TRAP*` FRU traps), one alert per slot, resolved by the module's online message or after 24 hours; a module that is inserted, booting or stopped by an operator raises nothing. The monitoring poll also reads the module status table over SNMP on Cisco IOS, IOS XE, NX-OS and IOS XR (`cefcModuleOperStatus`) and Juniper Junos (`jnxFruState`) and raises one critical `module_down` alert per module that is not working, resolved when the module reads OK, is disabled by an operator or leaves the table; it finds a module that never came up after a reload or whose message was lost. A module down or back online message re-polls the host within 5 seconds. `module_down` is also a metric for alert rules and suppressions. Other vendors, stack member state, supervisor redundancy and a module that disappears without ever reading not OK are documented gaps (`docs/vendor-monitoring-coverage.md#hardware-module-health`).
- SNMP traps are named and acted on (`docs/snmp-traps.md`). A received SNMPv1 or v2c trap is now stored with its MIB name and named varbinds (`linkDown: ifIndex 12, ifDescr GigabitEthernet1/0/12, ifAdminStatus up, ifOperStatus down`) instead of its size; an unknown trap is stored with its OID and varbinds. The registry covers the standard MIBs (SNMPv2-MIB, IF-MIB, ENTITY-MIB, BGP4-MIB, OSPF-TRAP-MIB, VRRP), net-snmp (OPNsense), Cisco, Juniper, Arista, Fortinet, Palo Alto, HPE Aruba (AOS-CX and AOS-Switch) and Netgear. SNMPv2c informs are now decoded and acknowledged. Ten built-in trap rules raise and resolve alerts (type `trap`, metric `trap_<rule>`): interface down, module down, power supply fault, fan fault, temperature alarm, BGP neighbor down, OSPF neighbor down, HA failover or switchover, device or agent restart, and repeated SNMP authentication failures. They are listed under **Monitoring > Configure > Syslog Rules** (**SNMP trap rules**), where each can be turned off or given another severity, and their metrics can be suppressed. A trap is acted on only when it comes from an inventory host and carries that host's SNMP community. A trap that names a state change re-polls the host within 5 seconds, and a configuration-change trap (Cisco, Juniper, Fortinet, AOS-CX, PAN-OS commit) starts the configuration backup and drift check, both through the syslog triggers' limits. A new switch, **Raise alerts from SNMP trap rules** (Settings > Syslog & Traps, on by default), turns the alerts off. Trap alerts are their own family: a syslog or polled alert for the same failure is separate, and a suppression of one does not cover the other. **Upgrade note:** the interface down rule alerts on a single `linkDown`; a device that sends link traps for its access ports raises one warning per port, so stop those traps on the device or turn the rule off. Fix: the Type filter of **Monitoring > Events** never showed traps (it asked for `snmp_trap`; they are stored as `trap`). Not run against live devices; ASA / FTD failover traps and the traps listed under "Known gaps" in the page are named only or not covered.
- SNMPv3 traps are authenticated, decoded and acted on (`docs/snmp-traps.md#snmpv3`, `docs/apc-ups.md`). An SNMPv3 trap from an inventory host is checked with that host's SNMPv3 poll user (the same user, protocols and passphrases; there is no separate trap user): user name, exact security level, HMAC (MD5, SHA-1, SHA-256, SHA-512), the RFC 3414 time window with a replay check, and decryption (DES, AES-128, AES-192, AES-256 in both key extension forms). A trap that passes is stored named and goes through the trap rules, the re-poll and configuration-change triggers and the APC UPS handler like a v1 / v2c trap with the right community. **Upgrade note:** every SNMPv3 trap used to be stored undecoded; now one from an inventory host that fails a check is dropped and counted (`trap_dropped_v3`, **SNMPv3 refused** under Settings > Syslog & Traps, which now also shows the wrong-community count). Set each device's trap user to the host's SNMPv3 poll user with the same security level. SNMPv3 informs are not answered or decoded (stored with their size); the replay record is in memory, so the first trap from each device after a restart is accepted without a time comparison. Not run against a live device.
- Polled power supply, fan, temperature, BGP and OSPF state (`docs/monitoring.md`, `docs/vendor-monitoring-coverage.md`). The monitoring poll now reads these state tables over SNMP and raises one alert per item, resolved when the item reads OK again: `power_supply_down` (critical), `fan_down` (warning), `temperature_alarm` (the device's warning or critical), `bgp_peer_down` and `ospf_neighbor_down` (critical). Power supplies and fans are read on Cisco (CISCO-ENVMON-MIB, else CISCO-ENTITY-FRU-CONTROL-MIB), Juniper (`jnxFruState`), Arista, PAN-OS (ENTITY-STATE-MIB), Fortinet (`fgHwSensorTable`), HPE Aruba AOS-Switch and AOS-CX, and Netgear managed switches; temperature on the same platforms except Juniper and AOS-CX. BGP peers (BGP4-MIB, and the Cisco, Juniper and Arista tables that also list IPv6 peers) and OSPF neighbors (OSPF-MIB) are read on every SNMP-polled host. A BGP peer that was never established is not alerted; an OSPF neighbor alerts after two polls in a non-healthy state, or when a neighbor that was healthy leaves the table. A table cut short by a timeout raises and resolves nothing, an empty table counts as "no items" at the third empty poll in a row, and a table a device never answers is then asked once an hour. The five counts and `module_down` are metric samples with hourly and daily rollups, and metrics for alert rules and suppressions. Hardware module health now runs on the same code. Not run against live devices; the per-vendor gaps are in the coverage matrix.
- Fix: a Meraki (or other integration) device added to the inventory keeps its look on the Topology map (`docs/meraki-topology.md#on-the-map`): it was redrawn as a plain inventory host, grey instead of the integration colour, without the red or amber border of a device its source reports offline or alerting, and a device without an icon (a camera, a sensor) as a dot instead of a square. Its tooltip now also names its source, status and site. The position it was pinned at is kept: the node gets its host id when it becomes a host, and a position saved under the id it had before is carried over (bulk **Add to inventory** and hosts added from the Inventory page lost it). A rebuild of the map after a refresh also keeps the nodes moved since the page opened.
- Link loss, latency and jitter for Meraki uplinks and Cato WAN links (`docs/meraki-topology.md#uplink-loss-and-latency`, `docs/cato-topology.md#wan-link-rtt-jitter-and-loss`, `docs/sla-monitoring.md`): each collection reads the five-minute history since the last stored sample, up to 6 hours: Meraki `devices/uplinksLossAndLatency` (loss and latency per MX uplink; Meraki reports no jitter and none is derived) and Cato `accountMetrics` (RTT, jitter and loss per Socket WAN link, the worse direction). Each bucket is stored once at its own time in the availability tracker's raw samples and daily rollups, so topology SLA targets for latency, jitter and packet loss now evaluate these links on the server. Optional per source (`include_uplink_metrics`, `include_link_metrics`, on by default); a refused call is a collection warning and does not stop the removal of entities that are gone.
